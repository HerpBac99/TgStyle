# Requirements Document

## Introduction

Модуль капсул (Capsules) в приложении TgStyle требует полного аудита и рефакторинга. Текущая реализация содержит запутанную логику, дублирование кода, костыли и неоптимальную архитектуру. Необходимо упростить, унифицировать и улучшить модуль для повышения поддерживаемости и производительности.

## Glossary

- **Capsule Module**: Модуль приложения для создания, редактирования и просмотра капсул стиля (образов из вещей гардероба)
- **Canvas Editor**: Редактор на основе Fabric.js для манипуляций с изображениями одежды
- **CapsulesManager**: Главный менеджер, координирующий UI, сервисы и обработку данных капсул
- **UIModalManager**: Универсальный менеджер модальных окон
- **Wardrobe Item**: Элемент гардероба (вещь одежды)
- **Generated Capsule**: Капсула, автоматически сгенерированная AI
- **Canvas State**: Состояние canvas (позиции объектов, масштаб, данные)
- **Thumbnail**: Миниатюра изображения капсулы
- **Background Removal**: Удаление фона с изображения

## Requirements

### Requirement 1

**User Story:** Как разработчик, я хочу иметь четкую и понятную архитектуру модуля капсул, чтобы легко поддерживать и расширять функционал

#### Acceptance Criteria

1. THE System SHALL разделить логику на специализированные модули с единственной ответственностью
2. THE System SHALL устранить дублирование кода между модулями
3. THE System SHALL использовать единообразные паттерны для работы с данными
4. THE System SHALL иметь четкую иерархию зависимостей между модулями
5. THE System SHALL документировать назначение каждого модуля

### Requirement 2

**User Story:** Как разработчик, я хочу упростить логику создания и редактирования капсул, чтобы уменьшить количество ошибок

#### Acceptance Criteria

1. THE System SHALL объединить дублирующуюся логику выбора вещей в единый компонент
2. THE System SHALL использовать единый flow для создания новой и редактирования существующей капсулы
3. THE System SHALL устранить костыли в обработке событий выбора вещей
4. THE System SHALL упростить навигацию между экранами (grid → selection → canvas → result)
5. THE System SHALL использовать единый механизм для работы с модальными окнами

### Requirement 3

**User Story:** Как разработчик, я хочу оптимизировать работу с Canvas Editor, чтобы избежать повторной инициализации и утечек памяти

#### Acceptance Criteria

1. THE System SHALL инициализировать Canvas Editor только один раз за сессию
2. THE System SHALL переиспользовать экземпляр Canvas Editor при переходах между экранами
3. THE System SHALL корректно очищать обработчики событий при скрытии canvas
4. THE System SHALL использовать единый метод для загрузки элементов на canvas
5. THE System SHALL устранить дублирование логики позиционирования элементов

### Requirement 4

**User Story:** Как разработчик, я хочу унифицировать работу с изображениями, чтобы избежать дублирования кода обработки

#### Acceptance Criteria

1. THE System SHALL использовать единый сервис для обработки изображений (resize, optimize, watermark)
2. THE System SHALL использовать единый механизм удаления фона
3. THE System SHALL кэшировать обработанные изображения для повторного использования
4. THE System SHALL использовать единый формат для передачи изображений между модулями
5. THE System SHALL оптимизировать размер изображений перед отправкой на сервер

### Requirement 5

**User Story:** Как разработчик, я хочу упростить взаимодействие между CapsulesManager и WardrobeManager, чтобы избежать дублирования логики

#### Acceptance Criteria

1. THE System SHALL использовать единый механизм для добавления вещей из гардероба
2. THE System SHALL устранить дублирование логики рендеринга грида гардероба
3. THE System SHALL использовать события для синхронизации данных между менеджерами
4. THE System SHALL избежать прямых зависимостей между менеджерами
5. THE System SHALL использовать общие сервисы для работы с данными гардероба

### Requirement 6

**User Story:** Как разработчик, я хочу упростить UIModalManager, чтобы избежать дублирования методов

#### Acceptance Criteria

1. THE System SHALL объединить дублирующиеся методы работы с модальными окнами
2. THE System SHALL использовать единый интерфейс для всех типов модальных окон
3. THE System SHALL устранить специфичные методы для canvas loading modal
4. THE System SHALL использовать композицию вместо наследования для расширения функционала
5. THE System SHALL упростить API для показа/скрытия модальных окон

### Requirement 7

**User Story:** Как разработчик, я хочу оптимизировать работу с состоянием canvas, чтобы избежать избыточных операций

#### Acceptance Criteria

1. THE System SHALL сохранять состояние canvas только при необходимости
2. THE System SHALL использовать инкрементальные обновления вместо полной перезагрузки
3. THE System SHALL кэшировать thumbnail изображения для предпросмотра
4. THE System SHALL избежать повторного удаления фона при редактировании
5. THE System SHALL использовать оптимистичные обновления для улучшения UX

### Requirement 8

**User Story:** Как разработчик, я хочу улучшить обработку ошибок в модуле капсул, чтобы пользователь получал понятные сообщения

#### Acceptance Criteria

1. THE System SHALL использовать единый механизм обработки ошибок
2. THE System SHALL показывать понятные сообщения об ошибках пользователю
3. THE System SHALL логировать детальную информацию об ошибках для отладки
4. THE System SHALL корректно восстанавливать состояние после ошибок
5. THE System SHALL использовать fallback механизмы при сбоях API

### Requirement 9

**User Story:** Как разработчик, я хочу упростить серверную часть API капсул, чтобы избежать дублирования кода

#### Acceptance Criteria

1. THE System SHALL объединить дублирующуюся логику валидации Telegram данных
2. THE System SHALL использовать middleware для общих операций
3. THE System SHALL вынести логику работы с файлами в отдельный сервис
4. THE System SHALL использовать единый формат ответов API
5. THE System SHALL оптимизировать запросы к базе данных

### Requirement 10

**User Story:** Как разработчик, я хочу улучшить тестируемость модуля капсул, чтобы легко писать и поддерживать тесты

#### Acceptance Criteria

1. THE System SHALL использовать dependency injection для внедрения зависимостей
2. THE System SHALL разделить бизнес-логику и UI логику
3. THE System SHALL использовать интерфейсы для абстракции зависимостей
4. THE System SHALL избежать прямых обращений к DOM в бизнес-логике
5. THE System SHALL использовать чистые функции где возможно
