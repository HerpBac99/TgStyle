# Правила разработки

## Язык коммуникации

Всегда отвечай на русском языке. Комментарии в коде на английском, документация и общение с пользователем на русском.

## Подход к задачам

### Уточнение требований

Если задача неясна или допускает множественные интерпретации:
- Задавай уточняющие вопросы ДО начала работы
- Лучше спросить, чем сделать не то, что требовалось
- Уточняй ожидаемое поведение при граничных случаях

### Декомпозиция задач

Для объемных задач:
1. Разбивай на атомарные шаги
2. Составляй план разработки с четкими этапами
3. Выполняй последовательно, проверяя результат каждого шага

### Анализ влияния изменений

Перед изменением кода:
- Найди все места, где используется изменяемый метод/модуль
- Проверь цепочки вызовов (если меняешь метод B, что будет с методом A, который его вызывает?)
- Используй `grepSearch` для поиска всех использований
- Проверь связанные UI компоненты и API эндпоинты

## Качество кода

### Обязательные принципы

1. **Чистота кода**: Выявляй и устраняй:
   - Костыли и временные решения
   - Дублирование кода
   - Мертвый код (неиспользуемые функции, импорты)
   - Устаревшие паттерны

2. **Переиспользование**: 
   - Перед созданием нового метода проверь существующие
   - Расширяй существующий функционал вместо дублирования
   - Каждый новый метод — потенциальное место для ошибок

3. **Правильность решений**:
   - Если работает — работает ПРАВИЛЬНО, не "как-нибудь"
   - Разбирайся в причинах проблем, не обходи их
   - Следуй архитектурным паттернам проекта

### Архитектурные требования

- Соответствие лучшим практикам 2025 года
- Singleton паттерн для менеджеров (экспорт экземпляра)
- Строгая типизация TypeScript (избегай `any`)
- Модульная архитектура (один модуль = одна ответственность)

## Процесс разработки

### После выполнения задачи

Обязательная рефлексия:

1. **Что сделали?** — краткое описание изменений
2. **Почему так?** — обоснование выбранного подхода
3. **Как можно лучше?** — возможные улучшения
4. **Проверка связей**: Все ли связанные места в коде проверены?
5. **Сборка**: Выполнен ли `npm run build` для проверки?

### Проверка изменений

После изменений:
```bash
npm run type-check    # Проверка типов TypeScript
npm run build         # Сборка проекта
```

Используй `getDiagnostics` для проверки ошибок в измененных файлах.

## Специфика Telegram Mini Apps

- HTTPS обязателен для production
- Используй Telegram WebApp API корректно
- Учитывай ограничения платформы (размер бандла, производительность)
- Тестируй в реальном окружении Telegram

## Запрещенные практики

1. Костыли и временные решения "лишь бы работало"
2. Добавление кода без анализа существующего
3. Создание дублирующего функционала
4. Игнорирование цепочек зависимостей
5. Пропуск проверки типов и сборки
