# План Масштабирования FastVLM Server
## От 1 до 4-8 одновременных запросов

### 📊 Анализ Текущих Ограничений

#### ❌ Проблемы Текущей Архитектуры:
1. **Последовательная обработка**: Flask обрабатывает запросы по очереди
2. **Неиспользованные возможности модели**: LLaVA поддерживает батчи, но мы передаем только 1 изображение
3. **Жесткий BATCH_SIZE = 1**: В конфиге прописан размер батча = 1
4. **Отсутствие очередей**: Нет буферизации запросов
5. **Неэффективное использование GPU**: Память очищается между каждым запросом

#### ✅ Доказанные Возможности:
1. **LLaVA поддерживает батчи**: `process_images(images, ...)` принимает список изображений
2. **GPU оптимизация**: Модель может обрабатывать несколько изображений параллельно
3. **Семафоры в оригинале**: LLaVA имеет встроенную систему контроля нагрузки
4. **Эффективная память**: `torch.stack()` объединяет изображения в батч

### ⚠️ Риски и Решения

#### Риск 1: Memory Overflow
**Причина**: Большие батчи занимают слишком много GPU памяти
**Решение**:
- Динамический размер батча в зависимости от доступной памяти
- Fallback на меньшие батчи при нехватке памяти
- Memory monitoring и автоматическое уменьшение размера

#### Риск 2: Несовместимые Изображения
**Причина**: Разные размеры/форматы изображений в батче
**Решение**:
- Предварительная нормализация изображений
- Группировка по размерам
- Отдельная обработка нестандартных изображений

#### Риск 3: Race Conditions
**Причина**: Многопроцессная архитектура
**Решение**:
- Использование Redis для координации
- Lock механизмы для shared resources
- Atomic operations для счетчиков

#### Риск 4: Model Corruption
**Причина**: Shared memory между процессами
**Решение**:
- Read-only sharing модели
- Separate model copies для каждого worker
- Regular health checks
